What Leaves With Them

When someone leaves, their team lead has to find out who owns each system now, and why. The answer is spread over chat, tickets and documents that disagree and keep changing.

67%

of 1,000 IT managers at large UK and US organizations worry about losing knowledge when people leave

64%

say their organization has already lost knowledge that way

Who it is for

A team lead handing over a leaver's work, or the new owner of a system. They ask in plain words: "Who owns billing-api now?" "Who decided ADR-0014?"

What it gives them

An answer they can check

Every cited claim comes with the record it rests on and the exact line, read again at its source before the answer is given.

A warning when a record changed

If a message was edited after the agents read it, the answer says so and flags it for a person. In our test the edited message was caught in 5 of 5 live runs.

The gaps, in writing

"fernhill-sso has no current owner. ... Nobody has been recorded as taking it over." Better to learn that before the last day than after.

The solution2/8

Two agents that check each other against the source

  • Investigator answers the question and backs every claim with a record id and the exact line it relies on.
  • Verifier goes back through Zetaris to the system that holds each record and checks that the line is still there. If it is not, the claim is rejected, whatever a model says.
  • A rejected draft goes back with the record as it reads now. The Investigator gets at most two more tries.
  • Only an answer whose every line held up is stored. Otherwise the answer lists what was dropped and why.

What comes back: the answer, each citation with its verdict, the dropped ones with the reason, the number of rounds, whether it was stored, and a trace of every step.

Agent workflow3/8

A loop, not a pipeline

Three systemsteam chat (Postgres)
tickets (CSV file)
documents (REST API)
all three registered in Zetaris
Memory graphbuilt from three SELECTs through Zetaris; the write gate (FalkorDB, pre-existing) decides what is kept
H-MEM adds earlier verified answers
Investigator21 graph tools → a draft answer with one quoted line per claim; Nemotron through Nightshift
draft ↓
Verifierre-reads each record by id through Zetaris → is the quoted line still there? (plain code, final) → model judgement (Nemotron through Nightshift)
Rejected → the Investigator gets the notes and each record as its source holds it now → revises (at most 2 revisions, so at most 3 rounds) → Verifier again
Every line held upstored as a finding and as an H-MEM memory
Some lines did notthe answer says what was verified and what was dropped, with the reason; nothing stored
Named in no systemone query across all three systems finds no record → the answer says so (absence_confirmed); nothing stored
Why a loop: a model can misquote a record or answer from an old copy. The loop turns that into a revision, and a quote that fails the check is never stored.

Sponsor technology5/8

Zetaris for every source read, Nightshift for every model call

Zetaris

  • Three SELECTs build the memory graph: 403 records, the same row counts as the source files (225 chat, 127 tickets, 51 docs)
  • The Verifier re-reads each cited record by id; median 0.20 s (chat) and 0.38 s (docs) in the 20 live runs of 24 Oct
  • Absence: one UNION ALL query across the three systems
  • Stop-gate check on 22 Oct, a script run before the agents were written: cross-system JOIN 45 of 45 rows; 8 of 8 quotes with one word changed were rejected

Meterless Nightshift

  • The main model provider for both agents; each agent has its own app id, allowed one model
  • 20 live runs: 95 answered model calls, 95 signed receipts, $0 each, 0 routing mismatches (1 more call came back empty and the code took that step)
  • Every response is checked: routed model, lane, cost 0; a mismatch stops the run, it is not hidden
  • Receipts signed (Ed25519) by the Nightshift daemon, one file per run, e.g. logs/receipts-20261024T133813Z-5253.jsonl

Meterless H-MEM + NVIDIA

  • H-MEM keeps answers that passed the gate and puts matching ones in front of the model before it answers
  • Each Verifier verdict on a recalled memory is feedback: "helpful" adds 0.05 to its confidence. A new memory starts at 0.70; in the cross-session proof one verdict took it to 0.75
  • Nemotron 3.5 Lightning: Investigator, 59 of 59 answered calls. Nemotron 3 Nano: Verifier, 36 of 36 (routed model, from the receipts)

What was unique6/8

The Verifier trusts the source, not the memory and not a model

Before any answer counts, the Verifier goes back through Zetaris to the system that owns each cited record and reads the line again. That check is plain code, and no model can overrule it.

On 24 Oct, in a development run before we moved to Nightshift (Nemotron 3 Nano on a local Ollama), the Investigator's model quoted a chat sentence as if it were ADR-0009, and the Verifier's model said "supports". The quote check rejected it anyway, and the revision quoted the ADR's own line.

Only answers whose every quote is still in its source reach H-MEM, so the agents' memory does not learn from a misquoted answer.

Tampered source: 5 live runs, 24 Oct (Zetaris, Nightshift, H-MEM)

msg-0148 edited in Postgres after the memory read it

  • Round 1: quote_not_in_record; the model's note: "Sana Petrov remains the owner"
  • Round 2: verified on ADR-0009; msg-0148 flagged on its own conflict line
  • Stored; the edit restored at the end

5 of 5 runs: round 1 rejected msg-0148, round 2 verified, restored. Median 164.5 s per question: the models think on every call and only one of the two was loaded at a time on our shared Mac. The film shows a later run of the same example (367 s), with the waits between outputs shortened.

A chat assistant over uploaded files (e.g. ChatGPT with file uploads)

Answers from the files it was given. It has no step that reads each quoted line again in the live system before the answer counts.

Wiki search (e.g. Confluence search)

Finds pages. The lead reads and reconciles them by hand; nothing reads a quoted line again at its source.

Future enhancements8/8

Next: real systems, same rule

In the product

  • Refresh the memory graph when the Verifier finds a record changed at its source (today the catch is reported and the graph keeps the old copy).
  • A Zetaris semantic layer with a read-only agent user, so the agents see only the views they need.
  • Absence checks that ignore letter case, and recall in H-MEM by meaning, not only by shared words.
  • Faster live runs: both Nemotron models loaded at once and thinking switched off per call (today a median of 18.4 s to 164.5 s per question).

With real teams

  • More sources behind Zetaris: meeting notes, end dates from the HR system, code ownership files.
  • A pilot on a real team's records, measured against the same benchmark questions.
  • Handover cards that the successor confirms, written back through the same gate.

Limits today

Source edits were tested on chat records only. H-MEM recall matches shared words, and the absence check is case-sensitive. Answer quality is bounded by the model: the guarantee is about what gets stored, not that every question gets answered.
